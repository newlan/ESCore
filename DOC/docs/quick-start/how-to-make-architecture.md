# 内容组织方式对比

同一个站点可以有多种内容组织方式，选哪种取决于内容规模和团队习惯。这里做个简单对比，也是本站当前选择的依据。

## 三种常见组织方式

| - | 单套文档（当前方案） | 多套文档（多实例） | 博客 + 文档 |
| --- | --- | --- | --- |
| 适用场景 | 一个产品、一套手册 | 多个产品线 / 多个角色（开发、运维、API） | 文档 + 持续更新的文章 |
| 配置复杂度 | 低，默认即可 | 中，需要为每套配置 `id` / `path` / `routeBasePath` | 低 |
| 侧边栏 | 一份 `sidebars.js` | 每套一份，互不干扰 | 文档一份，博客自动聚合 |
| 搜索 | 一次索引全部文档 | 一次索引全部，可控制路由 | 文档与博客一起索引 |
| 迁移成本 | 后续可拆成多套 | 前期配置略多 | 与单套相同 |

## 当前项目怎么选的

本站只有一套文档，所以直接用 `preset-classic` 的 `docs` 配置，侧边栏交给自动生成：

```js title="sidebars.js"
const sidebars = {
  docs: [{type: 'autogenerated', dirName: '.'}],
};
```

`docs/` 下的每个文件夹会变成一个可折叠分组，每个 `.md` 文件变成一个菜单项，排序由 front matter 里的 `sidebar_position` 决定。

## 什么时候该拆成多套文档

当出现下面任一情况时，建议用多实例（`@docusaurus/plugin-content-docs` 配置多个 `id`）：

- 有两条以上产品线，导航栏需要分成「开发文档 / 运维文档 / API 文档」；
- 不同文档需要不同的首页、面包屑、编辑链接；
- 不同团队各写各的，互不影响发布节奏。

写法示意（放在 `docusaurus.config.js` 的 `plugins` 里）：

```js
plugins: [
  [
    '@docusaurus/plugin-content-docs',
    {
      id: 'admin',
      path: 'admin',
      routeBasePath: 'admin',
      sidebarPath: './sidebarsAdmin.js',
    },
  ],
],
```

导航栏再用 `{type: 'docSidebar', sidebarId: 'adminSidebar', label: 'Admin 开发'}` 指向它即可。

## 建议

一个产品、一套手册，先用当前的单套方案；等内容真的长出第二条产品线，再拆分成多套，迁移成本很低。
