# 架构设计

ESCore 的架构目标不是把所有东西都做成微服务，而是让**实时通信、业务能力、设备接入与多端应用**在同一个工程体系里各就各位，并且能够随着规模增长逐步拆分。

## 总体架构

<ArchitectureFigure />

整体可以分为四层：

| 层次 | 职责 | 典型组件 |
| --- | --- | --- |
| 多端接入与安全层 | 终端连接、协议转换、身份认证、限流与权限 | Web、桌面端、App、小程序、管理后台、API 网关、JWT |
| 核心服务层 | 实时通信、业务领域服务、设备服务、文件消息、AI Agent | Socket.IO、Express 领域模块、MQTT、对象存储、模型服务 |
| 基础设施与数据层 | 持久化、缓存、对象存储、异步消息 | MySQL、Redis、对象存储、消息队列 |
| 运维与管理层 | 配置、日志、状态、API 文档与部署 | PM2、Nginx、Docker、日志与监控 |

## 多端接入层

ESCore 不假设终端类型，不同终端按能力选择协议：

- **Web / 管理后台**：HTTPS REST API + Socket.IO / WSS；
- **Windows / macOS 桌面端**：Electron 渲染进程复用 Web 能力，主进程补充原生能力；
- **iOS / Android App**：uni-app 打包，H5 端可直接使用 `socket.io-client`，原生端需要 Socket.IO 兼容客户端或网关适配；
- **微信小程序**：HTTPS + WebSocket，受平台域名白名单与协议限制；
- **IoT 设备**：MQTT 5 接入 EMQX，由后端设备服务消费与下发。

接入层的关键不是“支持多少个平台”，而是让账号、鉴权、消息格式与错误语义在各端保持一致。

## 安全与网关

生产环境通常由 Nginx 或云负载均衡承担入口职责：

```text
client
  │  HTTPS / WSS
  ▼
Nginx / API Gateway
  ├── /            → public/ 静态资源
  ├── /api/        → 127.0.0.1:3011
  └── /io          → 127.0.0.1:3012（WebSocket Upgrade）
```

建议在入口层完成：

- TLS 终止与证书管理；
- 请求体大小、超时与速率限制；
- 按路径路由到 HTTP API 或实时通道；
- 可信代理头、CORS 与 Origin 白名单；
- 访问日志与基础告警。

应用层仍需要做 JWT 校验、资源权限校验和业务参数校验，不能把安全完全交给网关。

## 核心服务层

### 实时同步服务

基于 uWebSockets.js（C++ `.node`）与 Socket.IO 协议层，负责：

- 长连接维护、心跳与断线重连；
- 房间 / 命名空间与租户隔离；
- 消息广播、在线状态与多端同步；
- 通过 Redis Adapter 在多个 Node 实例之间共享广播。

### 业务微服务

业务代码按领域模块组织，每个模块通常包含：

```text
Node/src/libs/api/<domain>/
├── controller / route   接口入口
├── service              领域逻辑
├── db                   数据访问
├── model / type         领域模型
└── index                模块装配
```

当前阶段这些模块运行在同一个 Node 进程中，共享数据库连接、配置、日志与实时上下文。它们的边界按领域划分，
当某个模块需要独立扩容或独立发布时，可以拆为单独进程或服务。

### IoT 设备服务

设备通过 MQTT 连接 EMQX，后端 `libs/sys/mqtt.ts` 负责：

- 设备上线、心跳与离线状态；
- 遥测数据接收；
- 指令下发与异步回执；
- 将设备状态写入数据库，并通过实时通道推送给管理端。

### 文件与消息服务

文件上传、对象存储、消息记录与多媒体处理属于通用能力。文件元数据通常落在 MySQL，文件本体放在对象存储，
大文件处理与转码应异步执行，避免阻塞实时通道。

### AI Agent 服务

通过配置模型服务的 `apiKey / baseURL / model` 接入模型能力。Agent 的流式结果通过实时通道推送给前端，
适合对话、问答、业务助手等场景。模型调用需要单独设置超时、重试、Token 限额与内容安全策略。

## 基础设施层

| 组件 | 作用 | 注意事项 |
| --- | --- | --- |
| MySQL | 账号、商户、订单、支付、权限、日志等业务数据 | 连接池、慢查询、备份与迁移 |
| Redis | 缓存、会话、在线状态与 Socket.IO Adapter | 持久化策略、内存上限、键前缀隔离 |
| 对象存储 | 图片、视频、附件 | 访问控制、CDN、生命周期 |
| 消息队列 | 异步任务、解耦与削峰 | 幂等、重试、死信队列 |
| Docker / Linux | 基础服务运行环境 | 资源限制、日志轮转、健康检查 |

## 三条典型数据流

### HTTP 业务请求

```text
Web / App
  │  HTTPS /api/orders
  ▼
Nginx
  │
  ▼
Express :3011
  │  JWT → 权限 → 参数校验
  ▼
订单领域模块
  │
  ├── MySQL：写入订单
  ├── Redis：更新缓存
  └── Socket.IO：推送 order:updated
```

### 实时消息广播

```text
终端 A
  │  socket.emit('message:send')
  ▼
Socket.IO :3012
  │  鉴权 → 校验 → 持久化
  ▼
房间 / 租户
  │
  ├── 终端 B / C 收到 message:new
  └── Redis Adapter 广播到其他 Node 实例
```

### IoT 设备上报

```text
设备
  │  MQTT publish device/{id}/telemetry
  ▼
EMQX
  │
  ▼
Node mqtt.ts
  │  解析 → 校验 → 入库
  ├── MySQL / Redis 更新状态
  └── Socket.IO 推送 device:updated 给管理端
```

## 从模块化单体到微服务

建议按下面的顺序演进，而不是一开始就拆分：

1. **模块化单体**：领域边界清晰、共享进程与数据库，开发和部署成本最低。
2. **读写分离 / 缓存分层**：先解决数据库与热点数据压力。
3. **实时通道水平扩展**：多个 Node 实例 + Redis Adapter + 负载均衡。
4. **按领域拆服务**：将高负载或高变更频率的领域拆出，使用 HTTP / 消息队列通信。
5. **服务治理**：在确有需要时引入注册发现、配置中心、链路追踪与分布式事务。

拆分的判断标准应该是：团队协作边界、发布频率、资源瓶颈与故障隔离需求，而不是“微服务”这个词本身。

## 扩展与约束

- **会话状态**：多实例下不要依赖单机内存保存会话，在线状态与广播通过 Redis 共享。
- **文件与日志**：容器化后使用对象存储 / 集中日志，不要把关键数据只留在容器内。
- **实时消息可靠性**：Socket.IO 默认不保证消息持久化，重要消息应先落库，再推送。
- **幂等**：支付回调、设备指令、消息重试都需要幂等键。
- **可观测性**：至少记录连接数、消息速率、错误率、Redis 延迟、MQTT 重连次数与接口 P95。
